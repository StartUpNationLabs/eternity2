# Vol-128 — ATLAS: Pattern-Database Heuristic

**Theme**: Korf-style pattern database for E2. Precompute admissible
patch-distance scores; replace naive "matched edges" with a smoother,
admissible heuristic.

**Per user binding** [[feedback_e2_one_invention_per_volume]]:
vol-128 is ATLAS-only.

## Why this is interesting

Vol-127 (CONCRETION) was refuted by structural counting. ATLAS is the
opposite end: instead of trying to compile away the search space, we
compute a *better gradient* over it. The Selby-Riordan piece set is
maximally branchy at the per-pair level (V127); but local patches
($k = 4-6$ cells) might have a non-trivial structure: each patch has
a minimum "edge correction" cost — the minimum number of edge changes
to make the patch consistent with some completion. This number is a
LOWER BOUND on the patch's contribution to total mismatches.

Summing patch-distances over all $k$-cell patches gives an admissible
heuristic $h(B) \le \text{mismatches}(B)$. Replacing the naive
mismatch count with this finer gradient should let ALNS distinguish
"close to good" from "near the wall" boards — a problem the current
ALNS doesn't see well (it just sees mismatch count).

## Plan (3 binding items)

1. **Patch enumeration**: define patch-shape (start with 2×2 = 4
   cells; later 3×2 = 6 cells). For each shape position on the 16×16
   board, the patch is a set of 4 cell-positions. Build all
   $\binom{256}{4}$ patches? No — only the GEOMETRIC patches
   (contiguous 2×2). On 16×16 there are $15 \times 15 = 225$ such 2×2
   patches.
2. **Pattern-DB**: for each 2×2 patch, enumerate all configurations
   $(p_1, r_1, p_2, r_2, p_3, r_3, p_4, r_4)$ where the 4 cells hold
   4 distinct pieces. For each config compute the patch's
   self-consistent mismatch count (4 internal edges in a 2×2 patch).
   The DB is keyed by patch-configuration; value = mismatch count.
3. **Online use**: score $h(B) = \sum_p$ patch-mismatch($B[p]$).
   Compare to naive mismatch count. Use $h$ as ALNS destroy-targeting
   metric — destroy where $h$ contributes most.

## Risks

- DB size: $\binom{256}{4} \times 4^4 \approx 1.7 \times 10^9 \times
  256 \approx 4 \times 10^{11}$ if we naively enumerate every
  $(p_1, ..., p_4)$ assignment. Too big. But the DB is queried by
  *what's actually in the board*, so a HASH MAP keyed by the 8-tuple
  $(p_1, r_1, ..., p_4, r_4)$ that ONLY stores realized patches is
  much smaller. We can compute on-the-fly per patch query (no
  preprocessing needed if it's fast enough).
- "Min correction to ANY completion" ignores the global piece-once
  constraint, which is fine for admissibility (it gives a lower bound).
