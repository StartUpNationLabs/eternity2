# AC-2001 / AC-3.1 (Bessière & Régin 2001)

**Status**: `unbuilt`, **top candidate for vol-24 propagator work**
**Origin**:
- Bessière & Régin, "Refining the Basic Constraint Propagation Algorithm", IJCAI'01
- Zhang & Yap, "Making AC-3 an optimal algorithm", IJCAI'01 (independent, same idea)
- Journal version: Bessière, Régin, Yap, Zhang, "An Optimal Coarse-grained Arc Consistency Algorithm", AIJ 2005
**Files**: — (target: `crates/propagators/src/ac2001.rs`)

## Definition

AC-2001 is **AC-3 + residual support**.

For every value pair `(xi, a, xj)` keep a single integer `Last[xi, a, xj]` = the smallest value `b` in `D_xj` known to support `(xi, a)`.

When revising arc `(xi, xj)`:
- For each `a ∈ D_xi`:
  - If `Last[xi, a, xj]` is **still in** `D_xj` → support intact, no check needed.
  - Else search `D_xj` for a new support **starting from `Last + 1`** (lex order). Set `Last` to the new support, or remove `a` if none.

The "start from Last+1" prevents AC-3's pathological re-scan and gives the AC-4 worst-case bound *with the coarse-grained simplicity of AC-3*.

## Complexity

- Time: **O(e·d²)** worst case — optimal, same as AC-4 / AC-6 / AC-7.
- Space: **O(e·d)** for the `Last` table. On E2: ~480 × 764 ≈ 367k entries — trivial.
- Per-revision cost in practice: dominated by the `Last`-still-valid check, which is one bitset-membership test on our [[bitset-domain-rep]].

## Variants

- **AC-3.2 / AC-3.3 / AC-3rm** (Lecoutre, Hemery 2007): different residue invalidation strategies. AC-3rm ("residue-multi") keeps Last but does **not** maintain it strictly — losses on worst-case bound, wins in practice because no per-removal bookkeeping.
- **Multidirectionality**: re-use Last entries across symmetric arc directions (Likitvivatanavong et al. 2003). Cheap and orthogonal.
- **AC-***: Van Dongen 2005 configurable framework that subsumes AC-3 / AC-2001 / AC-3rm under one skeleton with policy hooks.

## Implementation notes for E2

The "domain" of cell `c` is a bitset of (piece, rotation) tuples in `[0, 764)`. For an arc `(ci, cj)` over shared edge `k`:

```
Last[ci, t, cj] = first u ∈ D_cj such that piece_rot[t].color_on(edge k)
                  == piece_rot[u].color_on(opposite edge k)
                  AND piece(t) ≠ piece(u)   // alldiff side condition
```

Storage: `Vec<u16>` of length `n_arcs × max_domain`. Per restoration: trail-on-write the entries you bumped on this revision; revert on backtrack.

The "Last still in D_cj" check is `D_cj.contains(Last)` — a single bit test on a u64 word. **This is dramatically cheaper than AC-3's full color-class re-scan** on each revision, which is what the vol-16 `same_piece_rots` LUT was already trying to shortcut.

## Why this matters more than AC-6/AC-7

In our setting:
- Domains are large (d=764) and persistent across the search.
- Most propagation rounds delete only a handful of values per domain.
- AC-3 currently re-discovers the same supports thousands of times per node.

AC-2001 turns the inner support-search into amortized O(1) per still-valid `(xi, a)` — and *most are still valid* after a single piece commitment. This is precisely the regime where AC-3 wastes the most work.

## E2 applicability

**YES — implement. High EV.** Reasoning:

1. **Cheap port.** Coarse-grained loop = drop-in for existing AC-3 queue. No engine architecture change. Trail is a `Vec<(arc_id, value, old_last)>` segment per node.
2. **Strict improvement.** Same fixpoint as AC-3 (sound + complete arc-consistency), strictly fewer constraint checks. Cannot lose vs AC-3 on correctness; cannot lose on per-revision count.
3. **Hits the right hot path.** AC-3 is the dominant single-thread hotspot in `joe_depth150_par` (qualitative observation, **not yet quantified by flamegraph — see [[regin-ac-audit]] §1**). AC-2001 with bitset Last-check should give 2-5× CPU per AIJ'05 experimental tables (Table 2, MAC search: 1.5-9× across the RLFAP / random-CSP benchmarks; the 25× figure in some surveys refers to constraint checks, not CPU). The DOMINO pathological case in the same paper shows 25× CPU, but our problem is not that adversarial.
4. **Soundness under Blackwood:** Same caveat as AC-3 — AC-2001 is also unsound under break-allowance because it enforces strict edge-matching. Keep it OFF in `BLACKWOOD_RAW`, same gate as AC-3 / gacolor.

**Integration sketch (vol-24, ~2 days)**:
1. New crate module `propagators::ac2001` with `Last: Vec<u16>` indexed by `(arc_id × d_max + value)`.
2. Replace the AC-3 inner `find_support(t in D_ci, edge k, D_cj)` call with `lookup_or_update_last(ci, t, cj)`.
3. Backtrack trail: extend the engine's existing per-node trail with `last_changes: SmallVec<[(u32, u16, u16); 16]>`.
4. A/B benchmark via `bench-audit fleet` against `joe_depth150_par` baseline: expect ≥2× nps with identical solution counts.
